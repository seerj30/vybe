# ADR 0002: PostgreSQL schema and EF Core migrations

- Status: accepted
- Date: 2026-11-06
- Spec: [v1.3 §4](../spec/VYBE_Technical_Specification_v1.3.md), changelog v1.3.4

## Context

Spec v1.3 §4 defines the tables, constraints and invariants. The API (ASP.NET Core) needs a
schema it can migrate with expand-contract steps, and the rules must hold even when code is wrong.

## Decision

1. **EF Core code-first, Npgsql provider.** The model lives in
   [`services/api/src/Vybe.Data`](../../services/api/src/Vybe.Data). Migrations are generated with
   `dotnet ef`; [`services/api/db/schema.sql`](../../services/api/db/schema.sql) is the generated
   SQL for review (`dotnet ef migrations script`).
2. **Schema `vybe`, snake_case names** (EFCore.NamingConventions). No VYBE table is in `public`.
   On Supabase, `public` is exposed through the Data API; `vybe` is not, and the guards migration
   revokes all privileges from `PUBLIC`, `anon` and `authenticated`.
3. **Enum columns are `text` + CHECK**, not Postgres enum types. The CHECK lists are generated
   from the C# enums (`TextEnums`), so code and database cannot drift. Adding a value is an
   ordinary migration; removing one is expand-contract.
4. **Primary keys are UUIDv7**, generated by Npgsql on the client (time-ordered, no index
   fragmentation). Raw SQL that inserts rows (spec invariant 11) may use `gen_random_uuid()`.
5. **Foreign keys use RESTRICT, never CASCADE.** One deliberate gap: `challenges.winner_player_id`
   has no FK, because the FK check takes a KEY SHARE lock on the other player's row inside the
   recipient's verification and deadlocks crossed challenges (tested; the CHECK
   `winner_is_participant` keeps the reference valid). Code locks player rows with
   `FOR NO KEY UPDATE`, never `FOR UPDATE`. Two composite FKs are hand-written SQL because EF only
   models non-null alternate keys: the recipient run carries the challenge's id, and a purchase
   grant points at the buyer's ledger row for that item. The creator and recipient runs must
   belong to the right player and ruleset (EF composite FKs). Deletion and retention are explicit workflows
   (spec invariant 7, J4); a missing step fails loudly instead of deleting data silently. Every
   foreign key has an index that starts with its columns (tested).
6. **Database guards** (migration `DatabaseGuards`, hand-written SQL):
   - `wallet_transactions` and `admin_audit_logs` reject UPDATE, DELETE and TRUNCATE (append-only).
   - `game_rulesets` reject DELETE and any UPDATE except `retired_at` (immutable).
   - `game_sessions` in `verified`, `rejected` or `expired` reject any change except
     `review_flags` (spec invariant 6; anti-automation flags may arrive later).
   - A retired ruleset cannot be un-retired.
   - `version` (`game_sessions`, `challenges`) and `revision` (`wallets`, `avatar_configs`) are
     incremented by a trigger on every UPDATE; EF reads the new value back
     (`ValueGeneratedOnAddOrUpdate`). A compare-and-swap (spec invariant 5) therefore cannot pass
     twice, even when code forgets to increment the token.
   - Audit-log retention (spec §11, 90 days): DELETE is allowed only inside a transaction that ran
     `set_config('vybe.retention_delete', 'on', true)`. The ledger has no retention path.
   Triggers apply to every role, including the owner; a role-only scheme would not.
7. **Database defaults** for counters and flags (`xp_total`, `balance`, `revision`, `version`,
   `progress`, `attempts`, daily counters, `suppressed`), so the raw SQL upserts of spec invariants
   10 and 11 can insert only the columns they know.
8. **CHECK constraints beyond §4**, all implied by the spec text: handle format and
   `handle_normalized = handle`; state/field consistency (an `accepted` challenge has a recipient
   and deadlines; a `verified` session has a score, `verified_at` and `reward_day`;
   `rejected` ⇔ `rejection_reason`; a winner only on a `completed` challenge); the winner is a
   participant; creator and recipient sessions differ; SHA-256 hash lengths; `jsonb` columns hold
   objects and `equipped_json` has all slot keys and exactly two accessory points; trace size cap
   (16 KB); the ledger key matches the spec §4 table for its reason and reference.
9. **Invariant 9 in the database:** a partial unique index allows one `challenge_reward` per
   challenge across both players (`UNIQUE(player_id, ledger_key)` alone is per player).
10. **EF sentinels.** `level` and `min_level` have database default 1 but EF sentinel −1, so EF
    always sends the CLR value: a wrong 0 fails the CHECK instead of silently becoming 1.
11. **Player deletion is anonymization** (handle → reserved pseudonym `d_` + 18 random
    `[a-z0-9]`, enforced by `CHECK((status = 'deleted') = (handle ~ '^d_[a-z0-9]{18}$'))`). The ledger is append-only and references players with
    RESTRICT, so the J4 workflow clears personal fields (handle, display name, auth subject,
    avatar, reports' free text) and sets `status = deleted`; the player row and its pseudonymous
    id remain.

### Changes to spec v1.3 (applied as v1.3.4)

| # | Change | Reason |
|---|---|---|
| 1 | `saved_outfits.slot smallint CHECK (slot BETWEEN 1 AND 3)` + `UNIQUE(player_id, slot)` | Enforces "max 3 outfits" in the database, without a race between two concurrent saves. The API picks the lowest free slot; a unique violation means the limit was reached concurrently. |
| 2 | `catalog_items`: `CHECK (cardinality(compatible_body_presets) >= 1)` | Spec §9: every item declares compatible body presets. An empty array would make an item unequippable; the first test run caught this gap. |
| 3 | Append-only and immutability enforced by triggers | §4 said "append-only permissions" / "immutable" without a mechanism. |
| 4 | Tables in schema `vybe` | Keeps them out of Supabase's exposed `public` schema. |
| 5 | Version/revision incremented by trigger | Makes invariant 5 hold even when code forgets the increment. |
| 6 | Audit-log retention delete via `vybe.retention_delete` | §11 requires 90-day retention; the append-only trigger must allow exactly that. |
| 7 | J4 deletion = anonymization | The ledger is append-only and keeps a RESTRICT reference to the player. |
| 8 | Retention and sweeper indexes (`game_input_traces.received_at`, `admin_audit_logs.created_at`, suspended players) | §11 retention and the suspension sweeper must not scan whole tables. |
| 9 | No FK on `challenges.winner_player_id`; player locks use `FOR NO KEY UPDATE` | Invariant 10 (one player's rows per transaction) is otherwise false: the FK check deadlocks crossed challenges. |
| 10 | Idempotency: `locked_until` only while `in_progress`; completion is a CAS on the caller's lease | A takeover could otherwise capture a completed record and run the operation twice. |
| 11 | Audit-log retention deletes only rows older than 90 days | A session-level `SET` leaked on a pooled connection must not enable deletes of recent rows. |
| 12 | Finished-session guard compares a fixed column list | Expand/contract migrations must be able to backfill new columns on finished sessions. |

### Not created yet

- `friendships` (P1 in spec §4). Blocks live in `player_blocks`, which is MVP.

## Operations notes

- Lock player rows with `SELECT … FOR NO KEY UPDATE`. `FOR UPDATE` conflicts with the KEY SHARE
  locks of foreign-key checks in other players' transactions.

- Connection pooling: through Supavisor in transaction mode, set `Max Auto Prepare=0` (or use
  session mode) in the Npgsql connection string; named prepared statements break in transaction mode.
- The API should connect with a role that owns no tables; granting it the needed privileges is
  an infrastructure task (spec §13), not part of these migrations.
- `dotnet ef migrations add` needs no database. `dotnet ef database update` reads
  `VYBE_DB_CONNECTION`.

## Consequences

- A model change needs `dotnet ef migrations add <Name>` and a regenerated `db/schema.sql`;
  the test `Migrations_ApplyToCleanDatabase_AndMatchTheModel` fails if the model has changes
  without a migration.
- The integration tests (`Vybe.Data.Tests`) need Docker (Testcontainers, `postgres:17.6-alpine`).
- Errors raised by the guards use SQLSTATE `23000`; the API maps them to 500 `internal_error`
  (they indicate a bug, never a user error).
